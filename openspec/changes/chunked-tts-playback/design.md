## Context

Today's TTS pipeline is per-message and monolithic: `TtsNotifier.playNow`/`enqueue` hand `response.text` (raw markdown) straight to `TtsService.generate(text, messageId)`, which makes one call into `TtsIsolateWorker` and caches one `Uint8List` under `messageId`. Playback goes through `PlaybackService`, which already runs a FIFO queue of `PlaybackItem { id, content: Future<Uint8List> }` — built for sequencing whole messages in auto-playback mode, not for sub-message units.

The isolate worker (`tts_isolate_worker.dart`) processes `GenerateAudioMessage`s one at a time off a single `ReceivePort` — synthesis is inherently serial regardless of how many requests the main isolate fires off concurrently.

There is a separate, stale, unimplemented OpenSpec proposal (`streaming-tts-playback`, created 2026-03-03) that addresses playback-start latency via sample-level audio streaming from `sherpa-onnx`'s `generateWithCallback`. It has no code behind it (`PlaybackItem` has no stream field, `InMemoryAudioSource` just serves pre-built bytes). Per user direction, this change proceeds independently of it — no shared dependency, no attempt at compatibility with a design that may never be built.

## Goals / Non-Goals

**Goals:**
- Strip markdown formatting from message text before synthesis so it isn't read literally.
- Split long text into ordered chunks and start playback on the first chunk without waiting for the whole message to synthesize.
- Keep exactly one chunk's synthesis running ahead of playback (not the whole message at once).
- Let the user navigate within a message's chunks (back/forward) once it has playback focus.
- Do this within the existing `TtsService` / `TtsNotifier` / `PlaybackService` architecture — extend, don't replace.

**Non-Goals:**
- Sample-level audio streaming within a single chunk's synthesis (that's the separate, independent `streaming-tts-playback` proposal's concern).
- Full markdown AST fidelity for pathological/nested input — this targets well-formed LLM-generated markdown.
- Reordering or prioritizing the global auto-playback queue across different messages.
- Persisting chunk playback position across app restarts or navigation away from the chat screen.

## Decisions

**Hand-rolled text normalizer, not an AST-based one.** The set of markdown constructs to handle is small and fixed (headers, emphasis, links, code, tables, lists, blockquotes, rules). `gpt_markdown` (the existing rendering dependency) doesn't expose a reusable plain-text walker, and pulling in the `markdown` pub package to build/walk an AST for this bounded rule set is more machinery than the problem needs. Alternative considered: AST-based extraction — rejected as premature given well-formed input.

**Chunk boundaries: paragraph-first, sentence-fallback.** Split on blank lines; any paragraph exceeding `maxChunkLength` (~400 chars) is further split at sentence boundaries and regrouped. This matches how LLM responses are already structured (paragraphs are natural pause points) while bounding worst-case first-chunk latency for wall-of-text replies. Alternatives considered: fixed-length hard cuts (rejected — cuts mid-sentence, bad prosody) and sentence-grouping for everything (rejected — unnecessary complexity for already-short paragraphs).

**Explicit one-ahead prefetch in `TtsNotifier`, not implicit isolate serialization.** The isolate already processes requests serially, so in practice eager-vs-one-ahead mostly affects the main isolate's outstanding-Future bookkeeping rather than true parallelism — but explicit control is simpler to reason about (one in-flight generation per message at a time) and matches the requested behavior directly rather than relying on an incidental property of the isolate implementation.

**Chunk item IDs use a lookup map, not string parsing.** Per-chunk `PlaybackItem.id` is `'$messageId#$chunkIndex'`; routing playback events back to the owning message uses an explicit `Map<String, String>` populated at enqueue time, not by splitting on `#`, since message IDs aren't guaranteed not to contain that character.

**Per-chunk caching, LRU size 20 → 60.** Cache key becomes `'$messageId#$chunkIndex'`. Bumped so a handful of recent long (multi-chunk) messages stay replayable without regeneration; chunks are shorter than whole messages so total cached bytes stay roughly the same order of magnitude. `TtsService.cleanup()` — currently unused anywhere in the app — is updated to match by `'$id#'` prefix so it doesn't silently no-op if it's ever wired up.

**Forward = `skipCurrent()`, uniformly.** Because chunks are already enqueued in order in the shared playback queue (each one added as the previous one starts, for the prefetch), ending the current item early and letting the queue's normal advance-to-next-or-idle logic run is *the same operation* whether there's another chunk queued or not. No branching between "jump to next chunk" and "end the message" is needed at the call site.

**A backward jump clears the stale prefetched chunk first.** Because one-ahead prefetch means the chunk after the currently-playing one is often already sitting in the shared queue, `jumpQueue`-ing straight to a previous chunk would insert it *ahead* of that stale chunk — skipping the chunk in between on the next forward playthrough. `skipPreviousChunk` calls a new `PlaybackService.removeQueued(predicate)` primitive to drop any not-yet-playing items belonging to the same message before jumping, so one-ahead prefetch re-establishes cleanly from the new position. This was found during implementation, not anticipated in the original design pass; noted here for accuracy.

**Back uses a position snapshot, not a position stream.** `PlaybackService` gains a synchronous position read (pass-through to `just_audio`'s `AudioPlayer.position`), read once when the back button is pressed, rather than continuously observed. Simpler, and nothing in the button's behavior needs live position tracking. Threshold: >3s into current chunk → seek to chunk start; ≤3s and chunk index > 0 → `jumpQueue` the previous chunk (cache hit in the common case, since it just finished playing); ≤3s and chunk index 0 → no-op. One rule set, no separate special-casing for the position-0/chunk-0 no-op — it falls out of the same logic.

**Button visibility keyed to playback focus, not chunk count.** The back/play-pause/forward control shows whenever `MessageTtsState.status` is `playing` or `paused` for that message — including single-chunk messages, where back/forward remain meaningful (forward still ends playback early; back still no-ops or restarts). No `totalChunks > 1` gate, no disabled states for edge cases — those are behavioral no-ops, not disabled affordances. The 1-button ↔ 3-button swap animates (`AnimatedSize`/`AnimatedSwitcher`-style) rather than popping.

**Skip methods guard on playback focus as a safety net.** UI only renders the buttons when a message has focus, but `skipNextChunk`/`skipPreviousChunk`/forward handling in `TtsNotifier` also check that the target message currently owns the playing/paused item before acting, since the global auto-playback queue can hold other messages' chunks too.

**`playNow` clears the entire queue, not just the current item.** Found via user testing: play a message, then (without stopping it) navigate to a different chat and play a message there — the new message's first chunk played correctly, but the *second* thing heard was the previous message's leftover prefetched chunk, not the new message's second chunk. `jumpQueue` (which `playNow` uses to interrupt whatever's currently playing) only inserts the new item at the front; it never touches anything else already sitting in the queue, including a different message's one-ahead-prefetched next chunk. Since `playNow`'s whole contract is "stop whatever's happening and play this instead" (see its docstring), it now calls `PlaybackService.removeQueued((item) => true)` before `jumpQueue`, unconditionally dropping everything not-yet-playing regardless of which message it belongs to — narrower than `skipPreviousChunk`'s same-message-only predicate above, because `playNow`'s job really is "hard interrupt," not "resequence within one message." This is a pre-existing class of bug (any `jumpQueue` call could leave stale queue content behind for a different, unrelated message, e.g. from multi-message auto-playback queuing) that chunking's one-ahead prefetch made far more likely to trigger and notice.

**Chunking now normalizes per-paragraph, not on the whole message at once.** Added after initial testing surfaced two more requirements — pacing pauses (longer before headings) and highlighting the currently-speaking paragraph in the UI — both of which need to know which *original* paragraph each chunk came from. The chunker now: splits the **raw** message into paragraphs first (`splitRawParagraphs`, also used directly by the UI for rendering), normalizes each paragraph individually, and drops any that normalize to nothing (e.g. a paragraph that was only a code block) while preserving the original paragraph's index for the ones that remain. `SpeechChunk` carries that `sourceParagraphIndex` plus a `pauseAfter` hint (`none`/`paragraph`/`heading`) computed from whether the *next* paragraph is a markdown heading. Alternative considered: keep normalizing the whole text up front and only track index into the post-normalization chunk list — rejected because paragraph-level drops/merges would desync that index from the paragraphs the UI actually renders, silently highlighting the wrong text.

**Pauses are real silence appended to the WAV, not text tricks.** `sherpa-onnx`'s `generate()` takes a plain string with no SSML-like pause markup, so there's no way to ask the engine itself for "a longer pause here." Instead, `appendSilenceToWav` patches zero-amplitude PCM samples onto the end of a chunk's audio (250ms after a paragraph, 700ms before *and after* a heading, none between sentence-fallback sub-chunks of the same paragraph or after a message's last chunk) by editing the RIFF/data size header fields in place. Alternative considered: relying on the natural gap from `PlaybackService`'s lock release/reacquire between chunks — rejected because that gap is an implementation artifact (varies with device speed, and disappears entirely once the pre-existing lock-reacquisition bug above was fixed), not a controllable, message-content-aware pause.

**Durations are tuned by ear across devices/models, not fixed once.** First pass used 400ms paragraph / 700ms heading, with heading pause only applied *before* a heading (not after). Testing on a second device/model combination found the paragraph pause too long and a heading's own trailing pause missing (it fell back to the plain paragraph tier, since only the *next* paragraph's headingness was checked, not the current paragraph's own). Paragraph pause reduced to 250ms; a heading paragraph now also gets `ChunkPause.heading` as its own trailing pause (checked via `paragraph.isHeading || nextIsHeading` in `text_chunker.dart`, not just `nextIsHeading`), so headings get the longer pause symmetrically on both sides. These constants (`_clausePauseDuration`/`_paragraphPauseDuration`/`_headingPauseDuration` in `tts_provider.dart`) should be expected to need further by-ear tuning; there's no way to verify prosody without a listening pass on real hardware.

**Pause durations scale with the TTS speed setting.** The base durations (200/400/700ms) are wall-clock constants, but the user can set playback speed from 0.5x–2.0x (`settings.ttsSpeed`), which changes how many audio samples the model generates for a given amount of text — the WAV's sample rate doesn't change, only how much speech fits per second. An unscaled pause would feel disproportionately long at high speed and short at low speed. `pauseDurationFor(pause, speed)` (marked `@visibleForTesting`, called from `_buildChunkItem` with `service.speed`) divides the base duration by speed, so a pause stays proportionate to the surrounding sped-up/slowed-down speech.

**Punctuation-based pause cues use commas, not the original punctuation.** Colons (`Note: this matters`) and parenthetical/bracketed asides (`(like this)`, `[like this]`) are converted to comma-bounded clauses before synthesis — `Note, this matters` / `, like this,`. Commas are the most consistently pause-inducing punctuation across TTS engines; colons and bare brackets are comparatively under-modeled and don't reliably produce a pause. This is a best-effort heuristic, not verified against the actual model's prosody — the user is expected to report if specific cases still sound off.

**The colon "real pause" (layer 2) is a flagged, reversible experiment, currently off.** After testing on a second device/model combination, the 200ms appended silence after a colon-triggered clause split (see the Implementation Findings colon entry below) was reported as "irritatingly long" — a different verdict than the paragraph/heading pauses got. Rather than deleting the mechanism, `text_normalizer.dart` gates it behind `const _useRealColonPause = false`: off, a colon is comma-only (layer 1, whatever pause the model itself gives a comma); on, it also gets `clausePauseMarker` and the chunker's real-silence treatment (layer 2). The chunker's marker-splitting logic itself is untouched and still tested directly (`text_chunker_test.dart` constructs input with an explicit marker) so it doesn't bit-rot while dormant. This is an intentional A/B point, not a final decision — comma-only and real-pause should both get real listening comparisons before picking one for good.

**Colons additionally get a real, tunable pause — not just a comma.** After confirming paragraph/heading pauses sounded right, the user asked whether colon pauses could be made longer — they couldn't, because a colon only got "layer 1" (the comma substitution above), and there's no punctuation mark that reliably maps to a specific pause *duration*. So `_insertPauseCues` now also appends an invisible `clausePauseMarker` (U+2063) right after the colon's comma; the chunker splits a paragraph on that marker (in addition to its normal maxChunkLength/sentence-fallback splitting) so the leading clause becomes its own chunk with `pauseAfter: ChunkPause.clause` (200ms of real appended silence, same `appendSilenceToWav` mechanism as paragraph/heading pauses). Brackets deliberately do NOT get this treatment: wrapping an aside in the marker on both sides would split a sentence into three fragments (before/aside/after) for what's often a short parenthetical, risking choppier audio than the problem it solves — they stay comma-only. Trailing colons (marker with nothing after it, e.g. a heading ending in `:`) produce an empty split segment that's filtered out, not an empty trailing chunk.

**Paragraph highlighting reuses `splitRawParagraphs`, not a second parser.** The chat UI now renders one `GptMarkdown` per raw paragraph (`ChatMessageBubble`/`_AgenticMessageBubble`) instead of one `GptMarkdown` for the whole message, using the exact same `splitRawParagraphs` function the chunker uses — so a chunk's `sourceParagraphIndex` always names the same paragraph the UI is rendering, with no separate index-mapping logic to keep in sync. The active paragraph gets a tinted background while `MessageTtsState.hasPlaybackFocus` is true; otherwise no paragraph is highlighted. `getMessagePlaybackStatus: MessagePlaybackStatus Function(String)?` was renamed to `getMessageTtsState: MessageTtsState Function(String)?` (returning the whole state object) so the UI has `currentSourceParagraphIndex` without a second parallel callback. Padding is constant between highlighted and non-highlighted paragraphs (only the background color toggles) and there's no border — an earlier version varied padding and added a left border for the active paragraph, which shifted surrounding content on every highlight change; removed per user feedback.

## Implementation Findings

Two additional issues surfaced while building and testing the orchestration layer, beyond what was anticipated in this design:

- **Pre-existing bug in `PlaybackService._processNext()`**: it unconditionally re-requested the playback lock from `AudioCoordinator` for every item, including when `PlaybackService` already held it. `AudioCoordinator.requestPlayback()` denies a request unless the coordinator is idle, so `jumpQueue` — which deliberately keeps the lock across the swap rather than releasing and reacquiring it — was silently getting its new item denied and dropped whenever it interrupted something already playing. This affected the pre-existing "play now, interrupting current playback" feature (`TtsNotifier.playNow`), not just the new `skipPreviousChunk`; both rely on the same `jumpQueue` path. Fixed by skipping the redundant request when the lock is already held.
- **Transition-guard gap in `_handlePlaybackStateChange`**: the playing/paused status update (and prefetch trigger) was keyed only on "is the current item playing," not on whether this represented an actual transition. A queue-only mutation — e.g. `removeQueued` dropping a stale chunk during a backward jump, before `_processNext` gets around to reassigning `currentItem` — was misread as "this chunk just started playing again," re-triggering prefetch and resurrecting the very chunk that had just been removed. Fixed by gating on `prev.currentItem?.id != next.currentItem?.id || prev.status != next.status`.

Also worth noting: `apps/test/fixtures/audio_test_fixtures.dart`'s mock `AudioPlayer.stop()` didn't cancel the auto-complete timer scheduled by the preceding `play()`, unlike real `just_audio`. This caused stale completion events to surface well after a `stop()`/`jumpQueue`, producing flaky/misleading test failures unrelated to the logic under test. Fixed in the shared fixture (cancel the timer on `stop()`, `play()`, and `dispose()`), which benefits the whole suite, not just this change's tests.

- **`jumpQueue()` left the item it was interrupting behind as a zombie tail entry**: an earlier fix for cross-message queue bleed (see tasks.md §9.5) called `removeQueued((item) => true)` before `jumpQueue` to clear leftover queue content. But `removeQueued()` deliberately never touches `queue.first` — that's load-bearing for `skipPreviousChunk`'s "leave the actively-playing item alone, drop only its stale prefetch" use case. At the moment `playNow` called it, though, `queue.first` *was* the very item being interrupted, so it survived. `jumpQueue` then inserted the new item at position 0 without ever evicting it, so it sat one slot behind the new item and got played next once the new item finished — reproducing the original cross-message-bleed symptom (a stale chunk from the previous message audible right after the new message's first chunk) despite the 9.5 fix being in place. Root-caused via a from-source device install (ruling out a stale build) plus temporary trace logging showing the queue's actual contents at each step. Fixed inside `jumpQueue()` itself: it now drops the old `queue.first` (if any) as part of building the new queue, while still preserving any other, unrelated tail entries. A caller-side fix (calling `removeQueued` a second time, after `jumpQueue`) was tried first and rejected: it bumps `_queueChangeCount`, which races `_processNext`'s in-flight optimistic-concurrency check (`if (_queueChangeCount != initialVersion) return;`) and silently aborts the transition to the new item instead of fixing anything.

## Risks / Trade-offs

- [Sentence-boundary regex mis-splits on abbreviations/decimals ("e.g.", "3.14")] → Accept as best-effort; worst case is a slightly early/late chunk boundary, not corrupted speech content. Not worth a full sentence-tokenizer dependency for this.
- [Markdown normalizer sees malformed/unbalanced markers from an LLM] → Regex rules are written to fail closed (leave text mostly intact) rather than corrupt content on unmatched markers.
- [Larger LRU cache (60 vs 20 entries) increases peak in-memory audio bytes] → Chunks are shorter than whole messages, so total cached bytes stay in a similar range; revisit the constant if profiling shows otherwise.
- [Back/forward acting on the wrong message if the global queue advances mid-tap] → Mitigated by the focus guard at both the UI (button visibility) and notifier (action guard) layers.
- [Comma-substitution for colons/brackets, and the 400ms/700ms pause durations, are best-effort choices not verified against real synthesized audio in this environment] → Text-level transformation is unit-tested; actual prosody needs listening-based confirmation from the user, who can report specific cases that still sound off.
- [Splitting one `GptMarkdown` per paragraph instead of one for the whole message could change spacing/rendering for markdown constructs that span a `GptMarkdown` instance boundary in subtle ways] → Each raw paragraph (blank-line-delimited block) is still passed to `GptMarkdown` whole, so any single construct (list, table, etc.) stays within one paragraph and one widget; only inter-paragraph spacing is now explicit (`Container` margin) rather than implicit in one continuous parse.

## Migration Plan

Purely additive/internal — no persisted data format changes (the audio cache is in-memory and ephemeral) and no external API changes. Ships as a normal app release; rollback is a plain revert, no data migration in either direction.

## Open Questions

- Exact `maxChunkLength` (~400 chars) is a tunable constant, not user-facing — may need adjustment once tested against real message-length distributions.
- Whether forward/back should special-case a chunk still in `generating` status (audio not yet ready) beyond the existing "no current item → no-op" fallback — likely fine as-is, confirm during implementation.
- Image (`![alt](url)`) handling in the normalizer (speak alt text + "image" marker, or drop) was not explicitly confirmed by the user during design — proceeding with "speak alt if present, else drop" as a reasonable default; easy to change.
